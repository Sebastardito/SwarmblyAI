# Swarmbly AI 3.5.0 — Teams and trusted circles

**Language / Idioma:** [English](#english) · [Español](#español)

---

## English

**Released 2026-11-21.** DOI to be added once Zenodo mints it. The software for the private beta: trusted circles joined by invitation, also beyond the local network through the circle's own relay; node roles; teams with honest partial results; reciprocity credits; signed release artifacts and a beta kit. No sealed bank was run for this version, and the beta's exit criteria are still open (below).

### What changes

- **SwarmblyApp 0.8.0** ([release notes](https://github.com/Sebastardito/SwarmblyApp/releases/tag/v0.8.0)):
  - **Trusted circles.** Signed membership manifests, invitations by code or QR, and admission checked at the handshake and at the worker gate. New installations work only with the members of their circles; an existing installation keeps its previous mode until the user changes it.
  - **The circle as a destination.** A new destination class, `CIRCLE`: every send to a peer goes through the same destination policy as any other call, and the receipt names the circle and the member. Whether document passages may reach a circle is a setting of each circle.
  - **Beyond the local network, through the circle's relay.** The relay address and its certificate pin travel signed in the manifest and the invitation. The nodes' own TLS session runs end to end through the relay, so the relay sees who talks to whom and how many bytes, never the content. The owner's App pushes each new manifest version to the relay, so a revocation takes effect at once. The receipt lists the relay hop.
  - **Node roles.** Large model and reasoner, plus search and corpus executors that a node offers only when its owner switches them on. Tasks can ask for a role; a role never widens a permission.
  - **Teams and honest partial results.** A team is a stored plan template (roles, steps, dependencies) run by the existing scheduler. Each step ends complete, partial or failed; a step that depends on a failed one is blocked, never guessed, and the answer says which parts are missing.
  - **Reciprocity credits.** Signed, non-transferable receipts kept in a local wallet. A credit is offered only when the worker is busy, and a double spend is detected by the node that issued the receipt. The control messages are documented in a SPEC appendix.
  - **Sandbox prepared at first launch.** Recipe 5 no longer compiles the WebAssembly module inside a request. The App prepares it after start-up when at least 4 GiB of memory are free; below that it waits for the user, who can prepare it anyway (**Prepare anyway**, `--prepare-sandbox --force`).
  - **Doctor export** built from an allow-list: versions, system class, sandbox state and error codes, never names, addresses, paths, prompts, answers or keys.
  - **Leftovers of the 3.4 evaluation:** a tool that waits, is refused or stops is reported to the user; no raw tool block in an answer; a skill no longer displaces the document passages; the conversation language reaches every recipe; Cancel keeps the text already written; recipe 5 writes its script with the writer role and records the model actually used.
- **Circle relay** (`relay/`, new): members-only pairing proved by a fresh signed challenge and checked against the signed manifest; byte splicing without storing payload; authenticated owner manifest updates that revoke removed members; per-member limits and a push limit; a Dockerfile and a systemd unit. Where the relay runs is still to be decided.
- **Signed release artifacts** (`.github/workflows/release.yml`, `scripts/verify_release.py`, [`SIGNING.md`](SIGNING.md)): SHA-256 checksums and Sigstore keyless signatures for the installer bundle and the Docker image, attached to the published release or to a draft; the workflow never publishes a release itself. The Apple and Windows signing jobs run only once the maintainer's certificates are configured.
- **Installer:** Python 3.11 is required, and the sandbox is prepared at install time when memory allows.
- **Beta kit** ([`docs/beta/`](../beta/README.md), drafts): a guide for volunteers, consent and privacy, an install checklist, a feedback form and a beta bug template.
- **Benchmark:** a loopback two-node privacy mode; a pre-registered team-versus-local battery and a node-loss battery with checks for honest partial results; a guide for sealed bank v5; harness 1.4.1 (output files, needed material, exact numbers, correction turns, the model used per case).
- **Roadmap:** a light footprint is a later milestone, once the public network works: measured budgets per node class, starting with the sandbox compile and the size of the installed App.

### Change in behaviour

Recipe 5 needs the prepared sandbox. On a computer with less than 4 GiB of free memory the App does not prepare it on its own: until the user chooses **Prepare anyway**, recipe 5 is reported as unavailable, with the reason, and the request continues without it.

### How it was measured

- The test suites of the App (about 1,000 tests), the umbrella and the relay pass in continuous integration on Linux and macOS, and the two-node P2P tests also pass on Windows. They run real nodes over loopback with canned model answers: they check the instruments, not the models.
- The team-versus-local and node-loss batteries ran end to end on loopback with canned models only, to check their scoring.
- **Not measured yet:** no sealed bank was run for 3.5; the batteries have not run with real models; the relay and off-LAN circles have not run between real machines on different networks.

### Before the beta

The maintainer opens the Apple Developer and Windows signing accounts (until then the installers carry Sigstore signatures only, and macOS and Windows warn on first open); decides where the relay runs; runs the batteries and a circle between his own machines on different networks; runs sealed bank v5 once; reviews the beta kit; and invites the first circles.

### Limits

Alpha software. Nothing in 3.5 was measured with real models or on a sealed bank. Membership has no mutual TLS yet: a stolen node key can impersonate a member until the owner revokes it (R-010). Roles are declared by each node (R-011). The relay is a new public service run by the circle: it sees connection metadata, never content (R-015). Without the OS signing accounts, the installers are not notarised or Authenticode-signed (R-013). The 3.4 limits on exact results and the Windows disk guard still apply.

## Español

**Publicada el 2026-11-21.** El DOI se añade cuando Zenodo lo asigne. El software de la beta privada: círculos de confianza por invitación, también fuera de la red local a través del relé del propio círculo; papeles de nodo; equipos con resultados parciales honestos; créditos de reciprocidad; artefactos de publicación firmados y un kit para la beta. En esta versión no se corrió ningún banco sellado, y los criterios de salida de la beta siguen abiertos (abajo).

### Qué cambia

- **SwarmblyApp 0.8.0** ([notas](https://github.com/Sebastardito/SwarmblyApp/releases/tag/v0.8.0)):
  - **Círculos de confianza.** Manifiestos de membresía firmados, invitaciones por código o QR, y admisión comprobada en el saludo y en la puerta del trabajador. Las instalaciones nuevas solo trabajan con los miembros de sus círculos; una instalación existente conserva su modo anterior hasta que el usuario lo cambie.
  - **El círculo como destino.** Una clase de destino nueva, `CIRCLE`: todo envío a un par pasa por la misma política de destinos que cualquier otra llamada, y el recibo nombra el círculo y el miembro. Si los pasajes de documentos pueden llegar a un círculo es un ajuste de cada círculo.
  - **Fuera de la red local, por el relé del círculo.** La dirección del relé y el pin de su certificado viajan firmados en el manifiesto y en la invitación. La sesión TLS propia de los nodos va de extremo a extremo a través del relé: el relé ve quién habla con quién y cuántos bytes, nunca el contenido. La App del dueño envía al relé cada versión nueva del manifiesto, así que una revocación surte efecto en el acto. El recibo indica el salto por el relé.
  - **Papeles de nodo.** Modelo grande y razonador, más ejecutores de búsqueda y de corpus que un nodo ofrece solo si su dueño los activa. Una tarea puede pedir un papel; un papel nunca amplía un permiso.
  - **Equipos y resultados parciales honestos.** Un equipo es una plantilla de plan guardada (papeles, pasos, dependencias) que ejecuta el planificador existente. Cada paso termina completo, parcial o fallido; un paso que depende de uno fallido queda bloqueado, nunca se adivina, y la respuesta dice qué partes faltan.
  - **Créditos de reciprocidad.** Recibos firmados e intransferibles en una cartera local. Un crédito se ofrece solo cuando el trabajador está ocupado, y el nodo que emitió el recibo detecta un doble gasto. Los mensajes de control están documentados en un apéndice de la SPEC.
  - **La caja se prepara en el primer arranque.** La receta 5 ya no compila el módulo WebAssembly dentro de una solicitud. La App lo prepara tras arrancar cuando hay al menos 4 GiB de memoria libres; por debajo espera al usuario, que puede prepararla de todos modos (**Preparar de todos modos**, `--prepare-sandbox --force`).
  - **Exportación de diagnóstico** construida con una lista permitida: versiones, clase de sistema, estado de la caja y códigos de error; nunca nombres, direcciones, rutas, preguntas, respuestas ni claves.
  - **Pendientes de la evaluación de 3.4:** una herramienta que espera, es rechazada o se detiene se informa al usuario; ningún bloque de herramienta en bruto en una respuesta; una habilidad ya no desplaza los pasajes de los documentos; el idioma de la conversación llega a todas las recetas; Cancelar conserva el texto ya escrito; la receta 5 escribe su script con el papel de redactor y registra el modelo usado de verdad.
- **Relé del círculo** (`relay/`, nuevo): emparejamiento solo entre miembros, probado con un reto firmado nuevo y comprobado contra el manifiesto firmado; empalme de bytes sin guardar contenido; actualizaciones autenticadas del manifiesto por el dueño que revocan a los miembros retirados; límites por miembro y un límite de envíos; un Dockerfile y una unidad systemd. Dónde corre el relé está por decidir.
- **Artefactos de publicación firmados** (`.github/workflows/release.yml`, `scripts/verify_release.py`, [`SIGNING.md`](SIGNING.md)): sumas SHA-256 y firmas Sigstore sin clave para el paquete del instalador y la imagen Docker, adjuntas a la release publicada o a un borrador; el flujo nunca publica una release por sí mismo. Los trabajos de firma de Apple y Windows corren solo cuando los certificados del mantenedor estén configurados.
- **Instalador:** se requiere Python 3.11, y la caja se prepara al instalar cuando la memoria lo permite.
- **Kit de la beta** ([`docs/beta/`](../beta/README.md), borradores): una guía para voluntarios, consentimiento y privacidad, una lista de comprobación de instalación, un formulario de comentarios y una plantilla de errores de la beta.
- **Banco de pruebas:** un modo de privacidad con dos nodos en loopback; una batería preregistrada de equipo frente a ejecución local y una de pérdida de nodo con comprobaciones de resultados parciales honestos; una guía para el banco sellado v5; el arnés 1.4.1 (archivos de salida, material necesario, cifras exactas, turnos de corrección, el modelo usado por caso).
- **Hoja de ruta:** una huella ligera queda como hito posterior, cuando la red pública funcione: presupuestos medidos por clase de nodo, empezando por la compilación de la caja y el tamaño de la App instalada.

### Cambio de comportamiento

La receta 5 necesita la caja preparada. En un ordenador con menos de 4 GiB de memoria libre la App no la prepara por su cuenta: hasta que el usuario elija **Preparar de todos modos**, la receta 5 figura como no disponible, con el motivo, y la solicitud sigue sin ella.

### Cómo se midió

- Las suites de pruebas de la App (unas 1.000 pruebas), del paraguas y del relé pasan en integración continua en Linux y macOS, y las pruebas P2P de dos nodos pasan también en Windows. Ejecutan nodos reales por loopback con respuestas de modelo enlatadas: comprueban los instrumentos, no los modelos.
- Las baterías de equipo frente a local y de pérdida de nodo corrieron de principio a fin por loopback solo con modelos enlatados, para comprobar su puntuación.
- **Aún sin medir:** no se corrió ningún banco sellado para 3.5; las baterías no han corrido con modelos reales; el relé y los círculos fuera de la red local no han corrido entre máquinas reales en redes distintas.

### Antes de la beta

El mantenedor abre las cuentas de firma de Apple Developer y de Windows (hasta entonces los instaladores llevan solo firmas Sigstore, y macOS y Windows avisan al abrirlos por primera vez); decide dónde corre el relé; corre las baterías y un círculo entre sus propias máquinas en redes distintas; corre una vez el banco sellado v5; revisa el kit de la beta; e invita a los primeros círculos.

### Límites

Software alfa. Nada de 3.5 se midió con modelos reales ni con un banco sellado. La membresía aún no tiene TLS mutuo: una clave de nodo robada puede suplantar a un miembro hasta que el dueño la revoque (R-010). Los papeles los declara cada nodo (R-011). El relé es un servicio público nuevo que opera el círculo: ve metadatos de conexión, nunca contenido (R-015). Sin las cuentas de firma de los sistemas, los instaladores no están notarizados ni firmados con Authenticode (R-013). Siguen vigentes los límites de 3.4 sobre resultados exactos y el guardián de disco en Windows.
