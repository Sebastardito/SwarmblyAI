## English

**Released 2026-11-20.** DOI to be added once Zenodo mints it. Tools and data with code: one broker for every tool, an MCP client with approval per call, skills as instructions, author search with consent, a list on the swarm, a short script in an isolated sandbox, the Anthropic provider, an embeddings role and the agent runtime.

### What changes

- **SwarmblyApp 0.7.0** ([release notes](https://github.com/Sebastardito/SwarmblyApp/releases/tag/v0.7.0)):
  - **One tool broker.** Every tool call goes through the same broker, which applies the destination policy, records the approval and writes the receipt. The caller does not decide the tool kind.
  - **MCP client with approval per call.** Local servers are approved one by one, and a local tool may be set to "don't ask again in this project". Remote tools, the sandbox and author search always ask. A server whose manifest hash changes is suspended. The user sees the tool and its exact arguments before it runs; at most eight steps.
  - **Skills** in the open Agent Skills format (`SKILL.md`), instructions only. A skill is offered by its description, activated by the user and quoted in the prompt with a label that it cannot change permissions; importing a skill never runs anything.
  - **Author search with consent** (ORCID, OpenAlex, PubMed). The exact editable name, the services and the destination are shown before anything is sent; Cancel sends nothing. An ambiguous ORCID stops after the people search and returns candidates. The answer is a table built by code.
  - **Recipe 4, a list on the swarm.** Each item is answered with the project passages that are relevant to it. A local list never calls the swarm; a swarm list sends passages only with the third-party-passages permission. A wave in which every distinct item got one answer is retried item by item.
  - **Recipe 5, data with code.** The model proposes a short script for a CSV, a spreadsheet, a text document or the project's data. The user sees it and approves it with a one-time token; it runs in a WASI sandbox (`wasi-python` 0.1.5 over wasmtime) with no network, limits on time, memory and files, the data read-only and writes only to `/out`. The answer gives the script and its output, and up to two corrected scripts can be proposed.
  - **Models by role:** a native Anthropic provider (a third party, always) and an embeddings role through `roles.choose`. A passage reaches a third party only with both authorisations.
  - **Agent runtime:** `swarmbly-agent` 0.1.0 drives MCP tools in a conversation; the App supplies the broker as the tool executor, and the runtime runs nothing without an approved token.
  - **Python 3.11** is the minimum.
  - **Private glossary entries:** a line marked `| privado` (or the Private box) keeps the term and its equivalents out of every public query, reports them as removed, and still uses the entry for local answers.
- **swarmbly-agent 0.1.0** (in-tree, `SwarmblyCore/agent`): a dependency-free, local-only bounded loop with an injected model, tool executor and policy. Observations are quoted data, an approval pause returns a serialisable `RunState`, and the package has no network or subprocess code. It does not change the wire protocol.
- **SwarmblyLCE 0.2.1** unchanged (`050d4ed`, tag `v0.2.1`).
- **Two sealed banks (v4.1 and v4.2)** and harness 1.3.2, re-scored offline with 1.3.4 and read by an isolated judge.
- **Open batteries for recipes 4 and 5** and a v4 self-test bank, run on the fixed App.
- **Roadmap:** what 3.4 did not confirm moves to 3.5 (below).

### How it was measured

**Sealed banks v4.1 and v4.2**, each run once (32 cards × 3 repetitions, `qwen2.5:7b`, harness 1.3.2, App `ec3d206`), re-scored offline with harness 1.3.4 and read by an isolated judge who reported aggregates:

| | v4.1 | v4.2 |
|---|---|---|
| Cards × repetitions | 32 × 3 | 32 × 3 |
| Seal | OK | OK |
| Technical failures | 0 | 0 |
| The eight permission counters | 0 | 0 |
| Observations approved by the isolated judge | 22/96 | 44/96 |

- **Zero unauthorised sends was not met.** The public query **proposed by the App** kept a fragment of a private name: one card in v4.1 and two cards in v4.2, three repetitions each, and the simulated user approved each proposal as it was offered. This is the official result of the version; the fixes after the run are reported apart.
- **Zero permissions widened by data was met.** Tool descriptions, page content and skill text never widened a permission.
- **N7 was met:** no execution without approval, no network from the sandbox, and no writes outside `/out`.
- **Exact results ≥ 90 % in código-exacto was not met:** v4.1 0/9 and v4.2 6/12 with the 7B local model.

### Fixes after the banks

Measured only with open batteries until the next sealed bank:

- Private names are removed whole and by distinctive word, and the removed terms are shown to the user before the query is approved.
- Recipe 5 reads text documents, not only spreadsheets.
- The list recipe uses the relevant document passages for each item; a swarm list sends them only with the third-party-passages permission.
- A glossary entry can be marked private (`| privado`): it never reaches a public query and still serves local answers.

A new sealed bank on the fixed App confirms, or refutes, the privacy fix. The exact-result target with a 7B local model, the Windows disk guard (R-006) and the first sandbox compile (R-005) remain open.

### Limits

Alpha software. Exact results with a 7B local model stay below the 90 % target in código-exacto (v4.1 0/9, v4.2 6/12). The 3.4 privacy fix is not yet confirmed by a sealed bank: it was measured only with open batteries after the run that found the leak. The Windows disk guard is a watchdog, not a kernel file-size limit (R-006). The first sandbox run compiles the WebAssembly module: about 5 s and 3.3 GB of memory on an M-series Mac, about 60 s on a 2-vCPU Linux machine with 8 GB, once, then cached (R-005). A local MCP server runs with the user's rights; effective permissions are enforced at the tool level (approved tool list, schema on every call, manifest hash), not by an operating-system sandbox around the server (D-008). The banks were written by the maintainer, run with one model and one run per version.

## Español

**Publicada el 20-11-2026.** El DOI se añade cuando Zenodo lo asigne. Herramientas y datos con código: un único intermediario para cada herramienta, un cliente MCP con aprobación por llamada, habilidades como instrucciones, búsqueda de autor con consentimiento, una lista en el enjambre, un script corto en una caja aislada, el proveedor Anthropic, un papel de embeddings y el runtime de agentes.

### Qué cambia

- **SwarmblyApp 0.7.0** ([notas](https://github.com/Sebastardito/SwarmblyApp/releases/tag/v0.7.0)):
  - **Un único intermediario de herramientas.** Toda llamada a una herramienta pasa por el mismo intermediario, que aplica la política de destinos, registra la aprobación y escribe el recibo. Quien llama no decide el tipo de herramienta.
  - **Cliente MCP con aprobación por llamada.** Los servidores locales se aprueban uno a uno, y una herramienta local puede marcarse como «no preguntar de nuevo en este proyecto». Las herramientas remotas, la caja y la búsqueda de autor siempre preguntan. Un servidor cuyo hash de manifiesto cambia queda suspendido. El usuario ve la herramienta y sus argumentos exactos antes de que se ejecute; como máximo, ocho pasos.
  - **Habilidades** en el formato abierto Agent Skills (`SKILL.md`), solo instrucciones. Una habilidad se ofrece por su descripción, la activa el usuario y se cita en el prompt con una etiqueta que dice que no puede cambiar permisos; importar una habilidad nunca ejecuta nada.
  - **Búsqueda de autor con consentimiento** (ORCID, OpenAlex, PubMed). El nombre exacto y editable, los servicios y el destino se muestran antes de enviar nada; Cancelar no envía nada. Un ORCID ambiguo se detiene tras la búsqueda de personas y devuelve candidatos. La respuesta es una tabla armada por código.
  - **Receta 4, una lista en el enjambre.** Cada elemento se responde con los pasajes del proyecto que le corresponden. Una lista local nunca llama al enjambre; una lista en el enjambre envía pasajes solo con el permiso de pasajes a terceros. Una tanda en la que todos los elementos distintos reciben una misma respuesta se reintenta elemento por elemento.
  - **Receta 5, datos con código.** El modelo propone un script corto para un CSV, una hoja de cálculo, un documento de texto o los datos del proyecto. El usuario lo ve y lo aprueba con un token de un solo uso; se ejecuta en una caja WASI (`wasi-python` 0.1.5 sobre wasmtime) sin red, con límites de tiempo, memoria y archivos, los datos solo de lectura y escritura solo en `/out`. La respuesta da el script y su salida, y se pueden proponer hasta dos scripts corregidos.
  - **Modelos por papel:** un proveedor Anthropic nativo (siempre un tercero) y un papel de embeddings mediante `roles.choose`. Un pasaje llega a un tercero solo con las dos autorizaciones.
  - **Runtime de agentes:** `swarmbly-agent` 0.1.0 maneja herramientas MCP en una conversación; la App entrega el intermediario como ejecutor, y el runtime no ejecuta nada sin un token aprobado.
  - **Python 3.11** es el mínimo.
  - **Entradas privadas del glosario:** una línea marcada `| privado` (o la casilla Privado) mantiene el término y sus equivalentes fuera de toda consulta pública, los informa como eliminados y sigue usando la entrada para las respuestas locales.
- **swarmbly-agent 0.1.0** (en el árbol, `SwarmblyCore/agent`): un bucle acotado, sin dependencias y solo local, con modelo, ejecutor de herramientas y política inyectados. Las observaciones son datos citados, una pausa de aprobación devuelve un `RunState` serializable, y el paquete no tiene código de red ni de subproceso. No cambia el protocolo de red.
- **SwarmblyLCE 0.2.1** sin cambios (`050d4ed`, etiqueta `v0.2.1`).
- **Dos bancos sellados (v4.1 y v4.2)** y el arnés 1.3.2, repuntuados sin volver a correr con 1.3.4 y leídos por un juez aislado.
- **Baterías abiertas para las recetas 4 y 5** y un banco de autoprueba v4, corridos con la App corregida.
- **Hoja de ruta:** lo que 3.4 no confirmó pasa a 3.5 (abajo).

**Bancos sellados v4.1 y v4.2**, corridos una vez cada uno (32 fichas × 3 repeticiones, `qwen2.5:7b`, arnés 1.3.2, App `ec3d206`), repuntuados sin volver a correr con el arnés 1.3.4 y leídos por un juez aislado que informó agregados:

| | v4.1 | v4.2 |
|---|---|---|
| Fichas × repeticiones | 32 × 3 | 32 × 3 |
| Sello | OK | OK |
| Fallos técnicos | 0 | 0 |
| Los ocho contadores de permisos | 0 | 0 |
| Observaciones aprobadas por el juez aislado | 22/96 | 44/96 |

- **Cero envíos no autorizados no se cumplió.** La consulta pública **propuesta por la App** conservó un fragmento de un nombre privado: una ficha en v4.1 y dos fichas en v4.2, tres repeticiones cada una, y el usuario simulado aprobó cada propuesta tal como se ofreció. Es el resultado oficial de la versión; los arreglos posteriores se informan aparte.
- **Cero permisos ampliados por datos se cumplió.** Las descripciones de herramientas, el contenido de páginas y el texto de las habilidades nunca ampliaron un permiso.
- **N7 se cumplió:** nada se ejecuta sin aprobación, la caja no tiene red y no escribe fuera de `/out`.
- **Resultados exactos ≥ 90 % en código-exacto no se cumplió:** v4.1 0/9 y v4.2 6/12 con el modelo local de 7B.

### Arreglos posteriores a los bancos

Medidos solo con baterías abiertas hasta el próximo banco sellado:

- Los nombres privados se quitan enteros y por palabra distintiva, y los términos eliminados se muestran al usuario antes de aprobar la consulta.
- La receta 5 lee documentos de texto, no solo hojas de cálculo.
- La receta de lista usa los pasajes relevantes de los documentos para cada elemento; una lista en el enjambre los envía solo con el permiso de pasajes a terceros.
- Una entrada del glosario puede marcarse como privada (`| privado`): nunca llega a una consulta pública y sigue sirviendo para las respuestas locales.

### Pasa a 3.5

Un banco sellado nuevo con la App corregida confirma, o refuta, el arreglo de privacidad. El objetivo de resultados exactos con un modelo local de 7B, el guardián de disco en Windows (R-006) y la primera compilación de la caja (R-005) siguen abiertos.

### Límites

Software alfa. Los resultados exactos con un modelo local de 7B siguen por debajo del objetivo del 90 % en código-exacto (v4.1 0/9, v4.2 6/12). El arreglo de privacidad de 3.4 aún no está confirmado por un banco sellado: se midió solo con baterías abiertas después de la corrida que encontró la fuga. El guardián de disco de Windows es un vigilante, no un límite de tamaño de archivo del núcleo (R-006). La primera corrida de la caja compila el módulo WebAssembly: unos 5 s y 3,3 GB de memoria en un Mac de la serie M, unos 60 s en una máquina Linux de 2 vCPU y 8 GB, una vez, y después queda en caché (R-005). Un servidor MCP local corre con los derechos del usuario; los permisos efectivos se aplican a nivel de herramienta (lista de herramientas aprobadas, esquema en cada llamada, hash del manifiesto), no con una caja del sistema operativo alrededor del servidor (D-008). Los bancos los escribió el mantenedor, se corrieron con un solo modelo y una vez por versión.
