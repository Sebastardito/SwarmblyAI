# Decisions

Process and architecture decisions from release 3.4 on. Earlier decisions are in [`docs/ROADMAP.md`](../ROADMAP.md#decisions-behind-this-roadmap).

| ID | Date | Decision | Reason | Alternatives | Consequences | Revisit when |
|---|---|---|---|---|---|---|
| D-001 | 2026-11-18 | Development from 3.4 on is coordinated by an orchestrating agent, which delegates bounded tasks to a coding agent (DeepSeek Harness) | Long audits, implementation and test runs are done in parallel, and each result gets an independent review | One agent doing everything | Every task has a written contract and a review verdict; results are integrated only after verification | Review rejects too often, or costs outweigh the gain |
| D-002 | 2026-11-18 | The ledger lives in the umbrella, `docs/orchestration/`, versioned on `edge` | One public place for progress, decisions and risks across components | Local only; a private folder | It is written for the public: no conversations, no personal data, no sealed-bank content | Never contains anything private |
| D-003 | 2026-11-18 | The coding agent works on `dsh/…` branches in worktrees; reviewed work is integrated into the local `main` (SwarmblyApp, SwarmblyLCE) or `edge` (umbrella); the maintainer pushes | Keeps the main checkouts usable and every change reviewable | The maintainer merges every branch | Commits carry the maintainer's identity, are signed off and carry no agent attribution | — |
| D-004 | 2026-11-18 | Reasoning effort of the coding agent: high by default, max only for hard tasks or after a failed attempt | Cost against quality | Always max; low | — | Repeated failures at high |
| D-005 | 2026-11-18 | Recipe 5 sandbox: WebAssembly CPython (`wasi-python` over wasmtime) as the primary candidate, adopted only after a spike with escape tests passes on macOS, Linux and Windows; Docker as fallback; SQL-only as degraded mode | Only option that is the same on the three systems, with no network by construction and pandas included | Native sandboxes per system (three implementations, Windows weakest); SQL-only | The dependency is young (0.1.x, first release 2026-10-17, one maintainer, about 250 MB): pinned by version and hash, reviewed before adoption | The spike fails an escape test, or the project is abandoned |
| D-006 | 2026-11-18 | Python 3.11 becomes the minimum for SwarmblyApp | 3.10 lost security support on 2026-10-01; the MCP SDK documents 3.11+; `wasi-python` requires 3.11 | Keep 3.10 | `pyproject.toml`, installers and the doctor change; users on 3.10 must upgrade | — |
| D-007 | 2026-11-18 | The agent runtime is a separate package in SwarmblyCore, with no App dependency and apart from the measurement harness (ADR-001); local steps only in 3.4 | Keeps the instrument boundary and avoids a new App pin for every runtime change | Inside `swarmbly_v0`; in the App | The App passes the broker as the tool executor; a wire change needs a SWIP | A tool call must run on another node |
| D-008 | 2026-11-18 | For MCP, "effective permissions equal declared ones" is enforced at the tool level: approved tool list, schema checked on every call, manifest hash (a change suspends the server), destinations through egress | Achievable and testable in 3.4 | Also at the operating-system level (each server in a sandbox) | The app states that a local MCP server runs with the user's rights | Users ask for untrusted servers, or the sandbox from D-005 can host them |
| D-009 | 2026-11-18 | The coding agent works in full clones under `P2PAI/_wt/` (one per parallel stream), not in git worktrees; reviewed branches are fetched into the main checkouts | The agent's sandbox can write only inside its folder, and a worktree keeps its git metadata in the main repository, so it could not commit | Worktrees with commits made by the coordinator | Each stream has its own clone and branch; tests run with the umbrella venv and the clone first on `PYTHONPATH` | The sandbox allows writing worktree metadata |
| D-010 | 2026-11-18 | `wasi-python` 0.1.5 is adopted for recipe 5 on the spike's conditions: exact pins and wheel hash; each run in a disposable, pre-warmed worker process; a kernel file-size limit plus a size watchdog on the output folder; only `/data` (read-only) and `/out` granted; output collected without following links | The macOS spike passed 10 of 10 checks ([report](spikes/T7.0_wasi-python_macos.md)); the package does not limit disk writes (8–12 GB in about a second), so running it inside the app process is ruled out | In-process runs | A worker pool in the App; Linux and Windows checks run in CI before release; Windows needs its own disk guard (no file-size limit) | An escape on any system, or a Windows disk guard that cannot be made reliable |
| D-011 | 2026-11-18 | MCP tools reach a conversation through the agent runtime with approval per call: the model proposes a call, the user sees the tool and its exact arguments before it runs; at most 8 steps; only a local MCP tool can be set to "don't ask again in this project"; remote tools, the sandbox and author search always ask | Keeps "nothing runs without the user's yes" true for tools the model chooses, and makes the receipt match what the user saw | Approval once when the server is enabled; no model-driven calls in 3.4 (a button only) | The App adapter (T8.2) uses the runtime's `NeedsApproval` path for every call; the UI needs an approval card in the chat | Users find per-call approval too slow on local tools, or a measured study shows a safer default |
