# Decisions

Process and architecture decisions from release 3.4 on. Earlier decisions are in [`docs/ROADMAP.md`](../ROADMAP.md#decisions-behind-this-roadmap).

| ID | Date | Decision | Reason | Alternatives | Consequences | Revisit when |
|---|---|---|---|---|---|---|
| D-001 | 2026-11-18 | Development from 3.4 on is coordinated by an orchestrating agent, which delegates bounded tasks to a coding agent (DeepSeek Harness) | Long audits, implementation and test runs are done in parallel, and each result gets an independent review | One agent doing everything | Every task has a written contract and a review verdict; results are integrated only after verification | Review rejects too often, or costs outweigh the gain |
| D-002 | 2026-11-18 | The ledger lives in the umbrella, `docs/orchestration/`, versioned on `edge` | One public place for progress, decisions and risks across components | Local only; a private folder | It is written for the public: no conversations, no personal data, no sealed-bank content | Never contains anything private |
| D-003 | 2026-11-18 | The coding agent works on `dsh/…` branches in worktrees; reviewed work is integrated into the local `main` (SwarmblyApp, SwarmblyLCE) or `edge` (umbrella); the maintainer pushes | Keeps the main checkouts usable and every change reviewable | The maintainer merges every branch | Commits carry the maintainer's identity, are signed off and carry no agent attribution | — |
| D-004 | 2026-11-18 | Reasoning effort of the coding agent: high by default, max only for hard tasks or after a failed attempt | Cost against quality | Always max; low | — | Repeated failures at high |
| D-005 | 2026-11-18 | Recipe 5 sandbox: WebAssembly CPython (`wasi-python` over wasmtime) as the primary candidate, adopted only after a spike with escape tests passes on macOS, Linux and Windows; Docker as fallback; SQL-only as degraded mode | Only option that is the same on the three systems, with no network by construction and pandas included | Native sandboxes per system (three implementations, Windows weakest); SQL-only | The dependency is young (0.1.x, first release 2026-10-17, one maintainer, about 250 MB): pinned by version and hash, reviewed before adoption | The spike fails an escape test, or the project is abandoned |
| D-006 | 2026-11-18 | Python 3.11 becomes the minimum for SwarmblyApp | 3.10 lost security support on 2026-10-01; the MCP SDK documents 3.11+; `wasi-python` requires 3.11 | Keep 3.10 | `pyproject.toml`, installers and the doctor change; users on 3.10 must upgrade | — |
| D-007 | 2026-11-18 | The agent runtime is a separate package in SwarmblyCore, with no App dependency and apart from the measurement harness (ADR-001); local steps only in 3.4 | Keeps the instrument boundary and avoids a new App pin for every runtime change | Inside `swarmbly_v0`; in the App | The App passes the broker as the tool executor; a wire change needs a SWIP | A tool call must run on another node |
| D-008 | 2026-11-18 | For MCP, "effective permissions equal declared ones" is enforced at the tool level: approved tool list, schema checked on every call, manifest hash (a change suspends the server), destinations through egress | Achievable and testable in 3.4 | Also at the operating-system level (each server in a sandbox) | The app states that a local MCP server runs with the user's rights | Users ask for untrusted servers, or the sandbox from D-005 can host them |
| D-009 | 2026-11-18 | The coding agent works in full clones under `P2PAI/_wt/` (one per parallel stream), not in git worktrees; reviewed branches are fetched into the main checkouts | The agent's sandbox can write only inside its folder, and a worktree keeps its git metadata in the main repository, so it could not commit | Worktrees with commits made by the coordinator | Each stream has its own clone and branch; tests run with the umbrella venv and the clone first on `PYTHONPATH` | The sandbox allows writing worktree metadata |
| D-010 | 2026-11-18 | `wasi-python` 0.1.5 is adopted for recipe 5 on the spike's conditions: exact pins and wheel hash; each run in a disposable, pre-warmed worker process; a kernel file-size limit plus a size watchdog on the output folder; only `/data` (read-only) and `/out` granted; output collected without following links | The macOS spike passed 10 of 10 checks ([report](spikes/T7.0_wasi-python_macos.md)); the package does not limit disk writes (8–12 GB in about a second), so running it inside the app process is ruled out | In-process runs | A worker pool in the App; Linux and Windows checks run in CI before release; Windows needs its own disk guard (no file-size limit) | An escape on any system, or a Windows disk guard that cannot be made reliable |
| D-011 | 2026-11-18 | MCP tools reach a conversation through the agent runtime with approval per call: the model proposes a call, the user sees the tool and its exact arguments before it runs; at most 8 steps; only a local MCP tool can be set to "don't ask again in this project"; remote tools, the sandbox and author search always ask | Keeps "nothing runs without the user's yes" true for tools the model chooses, and makes the receipt match what the user saw | Approval once when the server is enabled; no model-driven calls in 3.4 (a button only) | The App adapter (T8.2) uses the runtime's `NeedsApproval` path for every call; the UI needs an approval card in the chat | Users find per-call approval too slow on local tools, or a measured study shows a safer default |
| D-012 | 2026-11-18 | Tests that need an optional extra ([tools], [agent], [sandbox]) skip without it; CI installs the extras so they run there | A [dev]-only install must collect and pass; CI must still exercise every path | Make the extras default dependencies | New tests must carry the skip; review checks it | An extra becomes a default dependency |
| D-013 | 2026-11-18 | The blind bank harness reaches simulated services through one launch-time test seam (`--test-host-map`, loopback targets only): policy, classification and receipts use the declared host; redirected entries carry `simulado: true`; a banner shows test mode; nothing in the UI, API or config can set it | The sealed bank v4 must exercise the third-party paths (remote MCP, author search) without real network and without a test-only path that real users could hit | A local TLS-intercepting proxy; per-tool base-URL settings | One small, auditable redirect point; the bank measures the real policy code | The seam is ever reachable without the launch flag |
| D-014 | 2026-11-20 | 3.4 closes by fixing the App defects the isolated judge confirmed on banks v4.1 and v4.2 (private fragments in the proposed public query; text documents in recipe 5; project documents in the list recipe), verifying them with open batteries, and publishing while stating that exit criteria 1 (zero unauthorised sends) and 3 (exact result ≥ 90 %) were not met on the sealed banks. Versions: SwarmblyApp 0.7.0, swarmbly-agent 0.1.0 (pinned by the App to the umbrella tag v3.4.0), Swarmbly AI 3.4.0, SwarmblyLCE unchanged at 0.2.1 | Sealed banks run once per version; the defects are understood and fixable; the same practice as 3.3 | Publish as is and move the fixes to 3.5; fix and write a new sealed bank before publishing | The 3.4 notes report the failed criteria; the fixes are measured only by open batteries until the next sealed bank | A new sealed bank runs on the fixed App |
| D-015 | 2026-11-21 | Circles are signed membership manifests (owner's Ed25519 key, members, expiry, version); invitations are signed tokens as file, short code or QR; admission is checked at the handshake and at the worker gate; new installs are circle-only by default; no mutual TLS in 3.5 | Today any peer that completes the handshake is accepted; the manifest reuses the existing identity and canonical signing | A node_id allowlist in settings; a circle CA with mTLS | Revocation by a new manifest version; tier stays GLOBAL; TRUSTED waits for mTLS | 3.6, when a per-circle key or mTLS is designed |
| D-016 | 2026-11-21 | Members off the LAN connect through an own rendezvous and relay service run by the circle owner: nodes register with an outbound connection, the relay pairs members of the same circle and splices the two connections, and the nodes run their normal TLS and channel-bound handshake through the splice; direct addresses are tried first; hole punching is a stretch goal | The maintainer chose to bring the relay into 3.5 rather than rely on an overlay network | Direct address or an overlay of the circle's choice; direct address only | A new public service with its own risks (R-015) and tests; the relay sees metadata, never content; the receipt lists it as a transport hop | If the relay delays 3.5, hole punching and public rendezvous move to 3.6 |
| D-017 | 2026-11-21 | A new destination class CIRCLE; peer sends go through egress.check_call; receipts name the circle and the member; passages reach a circle only with a per-circle switch circle_passages, off by default, separate from privacy.third_party_passages | Peers are hard-coded OWN_NETWORK today and peer sends bypass the policy gate; the third-party flag is about model services | Keep address-based classes; classify by transport | Honest receipts off the LAN; recipe 4 uses the new switch | — |
| D-018 | 2026-11-21 | Node roles (search, large model, reasoner, corpus) are self-declared in the signed advertisement with small validated metadata; placement uses them and tracks per-role success; roles never widen permissions; local executors make roles real on one node | Smallest MINOR-safe change; corpus metadata limited to a name and a size bucket | A separate signed role manifest with evidence; infer from model tags | Roles can mislead placement (R-011); measured by the team battery | When reputation or verification is designed |
| D-019 | 2026-11-21 | A team is a stored plan template run by the existing requester-central scheduler with role-aware placement; a task that cannot complete yields an honest partial answer instead of failing the request; no plan migration in 3.5 | Reuses Directory, retries and local rescue; meets the node-loss criterion | One-level delegation; replicated coordinator | A lost requester ends its run | When delegation (SwarmblyAgents) is designed |
| D-020 | 2026-11-21 | Reciprocity credits are signed, non-transferable task receipts issued by the requester to the worker, kept in a local wallet, expiring, spendable only by submitting work to the same circle; issuers keep logs to detect double spending inside the circle | SPEC §18 and GOVERNANCE: no transfer, no market, no premine | Local counters only; a shared ledger per circle | No global ledger; double spending detected, not prevented across circles | If circles federate |
| D-021 | 2026-11-21 | The task plane stays wire 0.2; circle control (manifests, invitations, credit receipts) uses new MINOR-safe message types on the same TLS session, documented as a SPEC appendix with conformance tests; the relay framing sits outside the end-to-end TLS | Fastest path; older nodes ignore unknown types | Protocol 0.3 now; a separate control protocol | Undocumented drift avoided by the appendix and tests | 0.3 with public rendezvous |
| D-022 | 2026-11-21 | Signed installers: the maintainer opens the Apple Developer Program (Developer ID, notarisation) and a Windows Authenticode certificate or Azure Trusted Signing; Linux and Docker artefacts get minisign or Sigstore signatures and SHA-256 checksums; signing runs in CI with secrets only the maintainer holds | The only way to avoid Gatekeeper and SmartScreen warnings; ≥ 90 % installs | Apple only; Sigstore and checksums only | Cost and CI secrets (R-013) | — |
| D-023 | 2026-11-21 | Relay operation for 3.5 (architect): the relay address and its certificate pin travel in the manifest and the invitation (a list, tried in order; two pins may overlap during rotation); the owner pushes each new manifest version to the relay over its authenticated session so revocation reaches the relay at once; members pair without a prompt (the App's own circle admission still applies on both ends); defaults 4 concurrent splices, 2 GiB per member per day, 300 s idle; port 8765 or 443 with TCP passthrough; metadata logs kept 7 days | Answers the spike's open questions that do not need the maintainer; who hosts the relay stays with the maintainer | Manual manifest copy; DNS SRV discovery; a prompt per pair | Revocation latency is one push; the privacy notice must name relay metadata | When public rendezvous arrives (3.6) |
| D-024 | 2026-11-21 | Swarmbly AI 3.5.0 (SwarmblyApp 0.8.0) is published as the software for the private beta with its exit criteria open: sealed bank v5 runs once and the team-versus-local and node-loss batteries run with real models before volunteers join; installs and severe bugs are counted during the beta | The maintainer approved the close; volunteers need a signed, tagged release to install, and the beta criteria can only be measured with the beta running | Hold the release until bank v5, the real-model batteries and the signing accounts | The release notes and roadmap decision 9 list each criterion as open; results come in a 3.5.x release or in the notes of the next one, published as they are | Bank v5 has run, or the first circle has joined |
| D-025 | 2026-11-25 | After bank v5: release 3.5.1 (App 0.8.1) with the high-severity fixes (private fragment and glossary-table definition in proposed queries, team status and reasoner capability, recipe-5 input paths and CSV sample), verified on open batteries and published stating that criteria 1 and 5 were not met on the sealed banks; harness 1.4.4 re-scores both runs; v5.2 is repeated in full (technical failure) with harness 1.4.4 and the published App 0.8.0 | Same pattern as D-014; the bank measures what was published, fixes are confirmed by a later sealed bank (v6) | Fix first and measure the fixes on v5.2 (rejected: v5.2 was written for 0.8.0 and has been seen by the judge only) | Medium-severity App defects (table correction, circle lists, preview sensitivity, month without year, abstention) move to 3.5.2/3.6 | Bank v6 or the first beta circle |
| D-026 | 2026-11-27 | The bank v5 measurement of App 0.8.0 is v5.1 (`20261123T072152Z`) and v5.2 (`20261123T073718Z`, 95/96 evaluable, one technical failure); the v5.2 run of 2026-11-25 (`20261125T201920Z`), which imported the 0.8.1 candidate, is set aside as a non-blind confirmation run and reported apart; no third run of v5.2 | Two banks exist precisely so that one incident does not invalidate the measurement (maintainer); a third run of a bank the judge has read twice adds little | Repeat v5.2 a third time with 0.8.0 | Release notes of 3.5.1 cite both 0.8.0 runs and the confirmation run apart | Bank v6 |
| D-027 | 2026-11-27 | Swarmbly AI 3.5.1 (SwarmblyApp 0.8.1) is published with the bank v5 results of 0.8.0 (criteria of zero unauthorised sends and exact results not met; circle, permissions and honest teams met), the open-battery numbers of 0.8.1 against 0.8.0 measured the same day, and the non-blind v5.2 repeat reported apart. The blind confirmation is a new sealed bank v6, run once on the published 3.5.1 | The fixes are only measured on open material written with knowledge of the defects; stating this keeps the claim honest | Wait for bank v6 before publishing; call the v5.2 repeat a measurement | Bank v6 must import the published App (`unset PYTHONPATH`, registry `componentes` line checked) |
