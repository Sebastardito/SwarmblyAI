# T10.5 — Relay design spike (WP3)

**Status:** design spike, 2026-11-21. Prototype and tests exist under `relay/`;
the App is not wired to it yet. This document is the input to the WP3
implementation task, not a released service.

**Inputs:** [`ARCH_3.5.md`](../ARCH_3.5.md) §3.2 (own rendezvous and relay),
§3.7 (wire), D-016 (own relay in 3.5), D-021 (task plane stays wire 0.2; relay
framing sits outside the end-to-end TLS) and R-015 (the relay is a new public
service). The manifest is being built in the App as
`swarmbly_app/p2p/circles.py`; the relay consumes it as a signed document and
does not import the App.

## 1. Problem and scope

A trusted circle has to work when members are not on the same LAN. The chosen
3.5 design (D-016) is an **own relay** run by the circle owner:

- every node keeps one outbound TLS connection to its circle's relay;
- the relay proves the node's Ed25519 key and checks it against the signed
  circle manifest it holds;
- two members ask the relay to pair, and the relay splices their two TCP
  streams;
- the nodes run their normal TLS 1.3 session and channel-bound handshake
  **through** the splice, so the relay forwards ciphertext;
- direct addresses are tried first; the relay is the fallback.

Goals:

1. The relay must not be able to read task payloads.
2. Only current circle members may register or pair.
3. A circle owner can deploy and operate it without a platform team.
4. Abuse and denial of service are bounded per member.
5. The relay stores no payloads and logs metadata only.

Non-goals for the first implementation: NAT traversal/hole punching,
multi-relay failover, a public registration service, reputation, billing, and
an App control-plane for manifests (WP1 owns that).

## 2. Topology and trust boundaries

```
 node A (circle member)                         node B (circle member)
 ┌─────────────────────┐                       ┌─────────────────────┐
 │ identity: Ed25519    │                       │ identity: Ed25519    │
 │ inner TLS 1.3 +      │                       │ inner TLS 1.3 +      │
 │ channel-bound hello  │                       │ channel-bound hello  │
 └─────────┬───────────┘                       └──────────┬──────────┘
           │  outer TLS 1.3, pinned relay cert              │
           │  register / pair / paired                      │
           ▼                                                ▼
      ╔══════════════════════════ relay ══════════════════════════╗
      ║ manifest (owner-signed) → membership checks               ║
      ║ control frames → pair → raw byte splice                   ║
      ║ sees: node ids, circle id, pair id, bytes, timing, IPs    ║
      ║ stores: in-memory counters only; no payload, no pcap      ║
      ╚═══════════════════════════════════════════════════════════╝
```

Trust boundaries:

| Boundary | What crosses | Protection |
|---|---|---|
| Node → relay | node id, circle id, signatures, ciphertext | TLS 1.3 with a pinned relay certificate; Ed25519 challenge |
| Relay → node | challenges, pair decisions, ciphertext | same |
| Node ↔ node | task plane, channel-bound handshake, payload | the existing TLS 1.3 + Ed25519 handshake, end to end; the relay is a byte pipe |
| Owner → relay | signed manifest file, TLS key | out-of-band deployment; manifest signature; file permissions |

The relay is **not** a certificate authority and does not authenticate the
node's TLS certificate. It authenticates the node's Ed25519 identity, exactly
as the App does at the application layer today. The nodes still run their own
handshake through the splice, so a relay that pairs the wrong peer cannot
complete the channel-bound handshake.

## 3. The relay's view of a circle manifest

The App owns the schema. The relay needs four facts: the circle id, the owner
key that signs the document, the member node ids, and the relay endpoint with
the certificate pin.

```json
{
  "circle_id": "circle-3f2a",
  "version": 4,
  "owner": "<owner node_id: base64url Ed25519 public key>",
  "members": ["<node_id>", {"node_id": "<node_id>", "name": "Ada"}],
  "expires_at": "2027-05-01T00:00:00Z",
  "relay": {
    "host": "relay.example.org",
    "port": 8765,
    "tls_cert_sha256": "<lowercase hex SHA-256 of the relay certificate DER>"
  }
}
```

**Signature.** The signature covers the canonical JSON of the manifest object:
sorted keys, compact separators, UTF-8, no ASCII escaping — the same rule as
`messages.canonical_bytes` in the App. It travels either as
`{"manifest": {...}, "sig": "<base64url>"}` or with `sig`/`signature` inside
the manifest. Verification uses the owner's Ed25519 public key, which is the
owner `node_id`.

**Tolerant, minimal parsing.** Because `circles.py` is still being built, the
parser accepts these aliases and ignores unknown fields:

| Fact | Accepted keys |
|---|---|
| circle id | `circle_id`, `id`, `circle` |
| owner | `owner`, `owner_node_id`, `owner_key`; owner may be a node-id string or an object with `node_id`/`public_key`/`key` |
| members | `members`, `member_node_ids`, `nodes`; entries may be node-id strings or objects with `node_id`/`id`/`public_key` |
| version | `version` (integer; default 0) |
| expiry | `expires_at`, `expiry`, `expires` (ISO-8601 or epoch seconds) |
| relay | `relay`, `rendezvous`; `host`/`address`, `port`, and `tls_cert_sha256`/`tls_sha256`/`cert_fingerprint`/`pin` |

Expiry is enforced when present. A malformed expiry is **refused**, not
treated as "never expires". An expired manifest refuses both registration and
pairing.

**Version and revocation.** A higher `version` replaces a lower one in the
relay's store. Revocation is a new signed version without the member; the
relay reloads changed files before every registration and pair request. A file
that fails verification is logged and ignored, and the previous valid version
stays in force until a valid replacement arrives, so a bad edit cannot open
the relay. The nodes independently check the manifest too (WP1), so a relay
that is slow to reload cannot by itself widen membership.

**Distribution.** The owner writes the manifest (or a directory of manifests)
on the relay host. Members get the manifest and invitation through the App's
control plane. The relay endpoint and pin may also travel in the invitation
(file, text code or QR), but the manifest is the authoritative copy for the
relay's membership checks.

## 4. Protocol

### 4.1 Transport and framing

- TCP, then TLS 1.3 on the node → relay leg. The relay presents a certificate;
  the client pins its SHA-256 (DER) from the manifest/invitation and compares
  it **before** sending the registration frame. The certificate may be
  self-signed: no public CA is required, which keeps deployment small.
- No client certificate. Node authentication is the Ed25519 challenge below.
- Control frames: 4-byte big-endian length + compact UTF-8 JSON object. The
  default maximum is 64 KiB. The relay never parses payload frames.
- After the `paired` frame, the connection is **raw bytes**: the two peers'
  streams are copied unchanged, in both directions.
- Minimum TLS version is 1.3 on both legs (outer and inner); there is no
  downgrade path.

### 4.2 Registration

```
client                                           relay
  │── register {v, circle_id, node_id} ───────────▶│  check manifest: member?
  │◀─ challenge {v, nonce} ────────────────────────│  32 random bytes, per connection
  │── register_proof {signature} ─────────────────▶│  verify Ed25519 over
  │                                                │  "swarmbly-relay-register-v1\n" +
  │                                                │  canonical({purpose, circle_id,
  │                                                │             node_id, nonce})
  │◀─ registered {circle_id, node_id} ─────────────│  mark authenticated
```

The challenge is generated per connection, kept only in memory, and consumed
by the successful proof. A captured proof replayed on a new connection fails:
the new connection has a different random challenge. The domain prefix stops
a signature made for another Swarmbly message from being reused here. The
challenge is not a bearer token: it is never sent to another party.

Refusals use an `error` frame with a stable code and then close:
`unknown_circle`, `not_a_member`, `manifest_expired`, `limit_bytes`,
`bad_register_proof`, `bad_frame`.

### 4.3 Pairing

```
 A (initiator)                relay                         B (responder)
  │── pair {circle_id, peer_node_id} ─▶│                          │
  │                                    │ pick an idle registered   │
  │                                    │ B connection; check both  │
  │                                    │ in the manifest; reserve  │
  │                                    │ splice slots and bytes    │
  │◀─ pair_wait {pair_id} ─────────────│── pair_incoming ────────▶│
  │                                    │◀─ pair_accept {pair_id} ─│
  │◀─ paired {role: initiator} ────────│── paired {role: responder}▶
  │════════════════ raw splice (inner TLS 1.3 runs here) ═════════│
```

Both the initiator and the named peer must be currently registered in the
same circle and present in the current manifest. A peer that is not connected
gets `peer_not_connected`; a node outside the circle gets `not_a_member`; a
node pairing with itself gets `self_pair`; a circle mismatch gets
`circle_mismatch`.

`pair_id` binds the `pair_accept` to the pending request. The responder's
`pair_accept` is required: the relay does not splice two members silently.
If the responder does not accept within the pair timeout, both sides get
`pair_timeout` and the reservations are released.

The inner TLS handshake starts only after `paired`; the relay is already in
raw-copy mode. Any control bytes buffered after `paired` are forwarded as
payload bytes; `read_frame` never reads past a frame.

### 4.4 Splice, close and limits

Two pumps copy `read(64 KiB)` chunks in opposite directions. The relay counts
both directions against both members' daily budgets, forwards, and repeats.
It does not buffer more than one chunk and does not write to disk.

| Limit | Default | Enforcement |
|---|---|---|
| Concurrent splices per member | 4 | reservation at pair time; `limit_splices` |
| Forwarded bytes per member per UTC day | 2 GiB | hard stop at the chunk that would exceed it; splice closes |
| Idle timeout | 300 s | no bytes in either direction; splice closes |
| Pair timeout | 30 s | both sides get `pair_timeout`; reservations released |
| Registration timeout | 10 s | connection closes |
| Control frame size | 64 KiB | `bad_frame`; connection closes |
| Connections per relay | 1024 | new connection closed immediately |
| TLS version | 1.3 | handshake fails below 1.3 |

When either pump ends (EOF, error, idle, budget), both sides are closed, the
pair is removed and both members' active-splice counters are released. A
restart resets byte counters; this is a budget, not accounting.

### 4.5 Versioning

Control frames carry `v` (currently 1). Unknown message types are refused with
`unknown_message`; unknown **fields** are ignored. The protocol is deliberately
separate from task wire 0.2 (D-021): only the relay and the WP3 client see it.
A future version can add direct-address candidates and hole-punch frames
without touching the task plane.

## 5. End-to-end channel and App integration

The relay terminates only the **outer** TLS. After `paired`, the client has a
socket-like stream; the node's existing TLS 1.3 layer runs over it. The bytes
on the relay side are therefore inner TLS records (`0x16 0x03 …`,
`0x17 0x03 …`), not task JSON. The channel-bound Ed25519 handshake then runs
inside that inner TLS exactly as on a direct connection, so the peer
authentication that exists today (TLS certificate fingerprint signed into the
hello/ack) is unchanged.

The prototype offers two integration routes:

1. `relay/tls.py` `TLSStream` uses `ssl.MemoryBIO` over the paired stream and
   exposes `do_handshake`/`sendall`/`recv`. The App adapts its
   `PeerSession.reader`/`writer` pair to it. This is the smallest change and is
   what the end-to-end test exercises.
2. `loop.start_tls()` on the existing asyncio transport, if it proves reliable
   when nested over the outer TLS transport. This would keep
   `asyncio.open_connection`-style readers/writers, at the cost of relying on
   an asyncio implementation detail.

Direct addresses remain first: the relay is used when the direct dial fails or
when the manifest has no usable endpoint hint. The App should not silently
fall back to a relay for a destination the user classified as local.

## 6. No payload storage, metadata-only logs

The production relay keeps:

- in-memory per-member counters (bytes today, active splices);
- the current manifests;
- the pending pair states;
- a logger.

It does **not** write payloads, packet captures, task frames or bytes to disk,
and the process has no writable path in the systemd unit. The only test hook
is `RelayServer._record_forwarded`, a no-op in production; the test subclass
copies the forwarded bytes to assert they are ciphertext. That hook must not
be enabled in a deployment.

Log lines contain: event, circle id prefix, node id prefix, pair id prefix,
peer IP:port, byte count, close reason. They never contain frame bodies,
signatures or payload. Recommended retention is the operator's choice; the
design assumes days, not months.

## 7. Deployment

**Host.** A small VPS or a home server with a forwarded port. CPU and memory
are not the constraint; bandwidth is. The relay does not need a database, a
writable disk or a public CA. One relay can hold several circles (one
manifest each); a circle owner normally runs one for their circle.

**Port.** 8765/TCP by default, reachable from members. Members connect
outbound, so their networks need no inbound port. If 8765 is blocked, change
`--port` and the manifest in the same version. 443 is possible but then the
relay needs the host's 443; document the choice rather than assume it.

**TLS.** A self-signed certificate is sufficient because members pin its
SHA-256. Generate it on the relay host, keep the key `0600`, and put the
fingerprint in the signed manifest. A publicly trusted certificate also works
and makes the pin easier to explain, but is not required. Renewal is a new
manifest version (new pin) distributed before the old certificate expires.

**systemd.** Install [`relay/deploy/swarmbly-relay.service`](../../../relay/deploy/swarmbly-relay.service)
at `/etc/systemd/system/`; it runs as `swarmbly-relay`, with a read-only
filesystem (`ProtectSystem=strict`), no capabilities, no home, and only the
manifest and TLS directories readable. `systemctl enable --now
swarmbly-relay`.

**Docker.** Build from the repository root with
`docker build -f relay/Dockerfile -t swarmbly-relay .`; mount
`circles/` and `tls/` read-only at `/etc/swarmbly-relay/`. The image runs as
UID 10001 with no shell.

**Owner checklist.**

1. Create a dedicated unprivileged user and the two directories
   (`circles/` 0750, `tls/` 0700).
2. Generate the relay certificate/key; record the SHA-256 DER fingerprint.
3. Add the relay host/port/pin to the circle manifest and sign it with the
   owner key (new `version`).
4. Write the signed manifest to `circles/` on the relay; validate the relay
   log says the circle loaded.
5. Open only the relay port in the firewall; confirm from outside with a
   port scan and a member registration.
6. Run the relay under systemd or Docker; confirm it starts after reboot.
7. Give members the new manifest/invitation; confirm a pair works from two
   different networks.
8. Revoke a test member by signing a higher version without them and confirm
   registration is refused after reload.
9. Decide log retention and monitor disk/CPU/bandwidth; alert on process
   exit and on a sustained connection count near the limit.
10. Keep the TLS key off backups that leave the host; the manifest is public
    and can be backed up normally.

**Upgrade.** Stop, replace the package/image, start. Pending pairs fail; nodes
reconnect. No payload or member history is lost because none is stored.

## 8. Threat model

Assets: payload and task content; membership (who may pair); metadata (who
talks to whom); availability. Adversaries: a non-member, a revoked member, a
network attacker, a malicious or compromised relay, a node with a stolen key,
and a DoS source.

| Threat | Mitigation | Residual / test |
|---|---|---|
| **Non-member pairing** | registration and pair both check the current manifest; peer must also be registered; `not_a_member`; test | a stolen member key is still a member (R-010); revocation is the answer |
| **Replayed registration** | fresh 32-byte challenge per connection, consumed, 10 s window; proof includes circle, node and nonce with a domain prefix; test replays a captured proof on a new connection | a stolen private key can register live, not replay |
| **Impersonation / MITM on the relay leg** | TLS 1.3 plus SHA-256 pin from the signed manifest/invitation; pin checked before any frame; test with a wrong pin | a compromised manifest can change the pin; the owner key is the root of trust |
| **Relay impersonates a node to its peer** | it cannot: the inner TLS channel-bound handshake authenticates the peer's Ed25519 key and certificate fingerprint through the splice | a malicious relay can still drop or delay traffic |
| **Malicious relay pairs the wrong peers** | pair ids bind sessions; both sides' channel-bound handshake fails against the wrong peer; the relay cannot forge the inner handshake | it learns that a pair was attempted (metadata) |
| **Malicious relay reads payload** | inner TLS is end to end; the relay only forwards records; test asserts captured bytes and logs do not contain the marker | traffic analysis and sizes remain visible |
| **Replay of pair / accept** | pair state is live, per connection, with a random `pair_id`; a `pair_accept` for an unknown or already-accepted pair is refused | a malicious relay can initiate pairing between two members; consent (`pair_accept`) is required |
| **DoS: connection flood** | global connection cap, registration timeout, small control-frame cap, TLS handshake timeout, systemd limits | no per-IP rate limit in the prototype; add a front proxy or per-IP counters before a public beta |
| **DoS: many pairs / large transfers** | per-member concurrent splice cap and daily byte budget; idle timeout; hard close | members can consume the relay's bandwidth up to their budgets; size the host for the circle |
| **DoS: slowloris on control** | registration and pair timeouts; no unbounded frame buffering | body reads are bounded by frame length and timeout |
| **Payload at rest** | no writes, no pcap, read-only unit, test hook is a no-op in production | operator could attach a debugger/tcpdump; trust the host or run it yourself |
| **Metadata exposure** | log prefixes only, no payload; the design is honest that the relay sees who/when/bytes | traffic analysis; a hostile relay operator can correlate |
| **Manifest tampering / rollback** | Ed25519 signature; invalid files ignored and the previous version kept; higher version wins; expiry and malformed-expiry refusal | a compromised owner key is game over (same as WP1) |
| **Revoked member keeps using an old manifest** | the relay reloads before every register/pair; nodes also compare manifest versions on the control plane | a race between revocation and an in-flight splice; close is next version's job |
| **TLS downgrade** | 1.3 minimum on both legs | none expected; test uses 1.3 |
| **Malformed control input** | frame size cap, JSON object check, unknown type refused, no eval | fuzzing still pending (open question) |

R-015 is the umbrella risk for this service. The implementation above covers
its listed mitigations: members only, per-member limits, no payload storage,
end-to-end TLS through the splice, its own suite, and the external port scan
before the beta (the scan is an operator checklist item, not code).

## 9. Hole punching later (stretch, likely 3.6)

The current protocol has the right rendezvous primitive: both members are
already registered on a relay with a live authenticated control channel. A
future version can negotiate a direct path and keep the relay as fallback:

1. Each node gathers local and server-reflexive UDP candidates (STUN-like,
   IPv4 and IPv6) and signs them with its node key.
2. `pair` gains a mode `direct`: the relay sends the peer's candidates, both
   sides send authenticated UDP probes, and the first successful path wins.
3. If the NATs are symmetric, both fall back to the TCP relay splice already
   implemented. The relay can also keep the signaling channel open so a
   failed punch does not need a new registration.
4. The direct path runs the same inner TLS 1.3 + channel-bound handshake, so
   the identity model and the task plane do not change. With QUIC, TLS 1.3 is
   built in and the handshake can be carried in the QUIC handshake.
5. The relay never sees direct payloads. It still sees signaling metadata
   unless the candidate exchange is encrypted to the peer (the node key makes
   that possible).

This is deliberately not in 3.5: it needs a UDP stack, NAT-type testing on
real networks, and much more failure testing. The TCP relay remains the
fallback and the correctness baseline. D-016 records that hole punching moves
to 3.6 if it is not ready.

## 10. Prototype map and tests

| Path | Purpose |
|---|---|
| `relay/protocol.py` | framing, canonical JSON, challenge signing/verification, error frames |
| `relay/manifest.py` | tolerant signed-manifest parser and versioned store |
| `relay/limits.py` | per-member splice and byte counters |
| `relay/server.py` | asyncio relay: register, pair, limits, splice, metadata logs |
| `relay/client.py` | App helper: connect, register, pair/accept, return a stream |
| `relay/tls.py` | `ssl.MemoryBIO` adapter for the inner TLS 1.3 session |
| `relay/tests/` | unit and loopback integration tests |
| `relay/deploy/`, `relay/Dockerfile` | systemd unit and image |
| `relay/README.md` | operator/developer quick start |

Run:

```bash
python -m pytest -q relay/tests
```

What the suite proves (33 tests at the time of writing):

- a signed manifest verifies, a tampered/expired/malformed one does not;
- registration succeeds with a signed challenge, and a captured proof
  replayed on a new connection is refused;
- a non-member cannot register; a pair to a non-member or to an unconnected
  member is refused;
- two members pair, both directions splice, and a **real TLS 1.3 session**
  with a test certificate completes through the splice (negotiated version
  asserted);
- the relay's captured forwarded bytes and its logs do not contain the inner
  plaintext marker;
- the concurrent-splice limit, the daily byte budget, the idle timeout and the
  control-frame size limit close the connection;
- a wrong certificate pin is refused before registration.

What is not proven yet: the App's actual channel-bound handshake through the
splice, a real multi-circle deployment, Windows, fuzzing, a long soak, and an
external port scan. Those are WP3 implementation/beta tasks.

## 11. Open questions for the architect

1. **Who hosts the relay?** The circle owner (D-016) is the default. Does the
   project also run a community relay, and if so who is accountable for abuse
   and for the metadata it sees?
2. **How does the App discover the relay address?** Manifest
   (`relay.host`/`port`/pin), invitation only, a DNS `SRV` name, or a
   user-entered address? The relay's own unit assumes the manifest, but the
   invitation path needs a decision.
3. **IPv6:** should the relay listen on v6 by default, and should the manifest
   carry separate v4/v6 endpoints? The prototype binds `0.0.0.0` and supports
   `AF_INET6` in the unit but has no v6 test.
4. **One relay per circle or several?** Failover needs either a manifest list
   or a directory service; the current protocol has one endpoint.
5. **How does the relay learn a new manifest version?** Manual file copy
   (prototype), SIGHUP, an authenticated control API, or pulling from the
   owner? Manual is safe but revocation latency is the owner's.
6. **Should the relay authenticate the owner/operator** for manifest updates,
   or is filesystem access the only control plane? The prototype has no admin
   interface, which is the smallest attack surface.
7. **App integration:** `ssl.MemoryBIO` adapter (prototype) versus
   `loop.start_tls()` on the existing transport. This determines how much of
   `transport.py` changes and whether the existing `PeerSession` can be
   reused unchanged.
8. **Pair consent UI:** the responder must accept. Is a per-circle setting
   "accept pairs automatically from members" acceptable, or does every pair
   need a visible prompt? The prototype requires an explicit `pair_accept`.
9. **Limits:** are 4 concurrent splices, 2 GiB/day and 300 s idle right for a
   20–50 person beta? They are configurable, but the defaults are a policy
   choice.
10. **Port and hostname:** 8765 is easy to explain but often blocked; 443
    needs the host. Should the relay ship with a recommended reverse-proxy
    setup (which would break raw TLS pinning unless it is TCP passthrough)?
11. **Certificate rotation:** a new pin needs a new manifest version. How long
    should the old and new relay certificates overlap, and should members
    accept a manifest that pins both?
12. **Logging and retention:** how long may the operator keep IP/timing
    metadata, and what do the privacy notice and consent form say (R-014)?
13. **Abuse handling:** what does a circle owner do with a member who floods
    the relay? Revocation is the only lever today; is a per-member throttle
    enough before a public beta?
14. **Protocol 0.3:** D-021 keeps the task plane at 0.2 and puts relay framing
    outside it. Does the relay control protocol need its own version registry
    and conformance tests now, or when direct paths arrive?
15. **Public port scan and fuzzing:** who runs the external scan before the
    beta, and is a fuzz target for the frame parser part of WP3 or WP8?
